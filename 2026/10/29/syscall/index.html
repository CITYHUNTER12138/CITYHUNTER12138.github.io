系统调用的执行流程：从用户态请求到内核返回

前置概念

系统调用（System Call）是操作系统内核向用户程序提供的接口。程序通过它请求文件读写、内存映射、进程创建等操作。与普通函数调用相比，系统调用需要跨越用户态和内核态，由内核校验请求并执行相应服务。

用户态与内核态是 CPU 的两种执行权限状态。在通常的 Linux x86-64 环境中，用户程序运行在 Ring 3，内核运行在 Ring 0。用户态不能执行特权指令，也不能直接访问受保护的内核内存。内核态允许操作这些资源，但仍受地址映射及相应硬件保护机制约束。

libc是 C 标准库及相关操作系统接口的用户态实现。应用调用的 read() 通常是 libc 提供的封装函数，对应的内核函数在更深一层。

系统调用号与 ABI决定了请求的二进制形式。系统调用号标识具体请求；ABI（应用二进制接口）规定调用号、参数和结果如何传递。系统调用 ABI 与普通函数调用 ABI 并不完全相同。

寄存器与执行现场：寄存器是 CPU 保存当前计算状态的位置。除参数和结果外，CPU 还需要记录下一条指令的位置、栈的位置以及标志位等信息。这些与继续执行相关的状态构成执行现场。在 x86-64 上，rip 是指令指针，rsp 是栈指针，rax 常用于保存结果。

用户栈与内核栈是分别用于用户代码和内核代码执行的栈。Linux 为线程分配内核栈，系统调用的内核函数调用和部分现场保存在这块栈上。struct pt_regs 是内核使用的寄存器现场结构，保存通用寄存器及指令地址、栈指针、标志等信息，不包含浮点、向量寄存器的完整状态。

文件描述符（fd）是进程访问已打开文件对象的整数标识。它可以指向普通文件，也可以指向管道、socket 或设备。read(fd, buf, count) 表示从该对象读取最多 count 字节，写入用户缓冲区 buf。

这里以 Linux x86-64 的传统 SYSCALL 入口为例，C 层分发参考 Linux 6.12。流程分为“请求准备、进入内核、内核执行、返回用户态”四个阶段。沿正常返回的 read 路径说明。

阶段二：进入内核并保存现场

从用户态到内核态的转换由硬件和内核入口代码共同完成。硬件负责受控地改变权限和执行位置，入口代码负责建立执行内核函数所需的环境。

CPU 完成权限切换

内核初始化时，会通过模型专用寄存器（MSR）配置系统调用入口。其中，IA32_LSTAR 保存入口地址，其他相关寄存器配置段选择子和进入内核时需要屏蔽的标志位。

CPU 执行传统 x86-64 的 syscall 指令时，主要完成：

  1. 将 syscall 后面那条指令的地址保存到 rcx；
  2. 按架构规则将标志状态保存到 r11；
  3. 切换到内核特权级，更新相关段状态和标志；
  4. 跳转到内核配置的入口地址。

入口地址由内核预设，用户程序不能通过传递一个函数地址，让 CPU 以内核权限任意跳转。用户只能按照系统调用接口表达请求。

传统 syscall 指令不会自动切换 rsp，也不会把完整现场压入栈。CPU 到达内核入口时虽然已有内核权限，但 rsp 仍是用户栈指针。[2]

入口汇编建立内核环境

Linux 的 entry_SYSCALL_64 用汇编完成后续准备。在这条路径中，其主要工作按依赖关系包括：

  1. 通过 swapgs 切换 GS 基址，以访问当前 CPU 的内核私有数据；
  2. 暂存用户栈指针；
  3. 启用内核页表隔离（KPTI）时，切换到内核侧页表；
  4. 加载当前线程的内核栈指针；
  5. 在内核栈上构造 pt_regs，保存后续处理和返回需要的现场。

页表规定虚拟地址到物理内存的映射及访问权限。这里的条件性页表切换属于同一线程的用户侧、内核侧映射转换，不代表切换到另一个进程。

构造现场时，原始调用号会保存在 orig_ax 中，而返回值最终写入 ax 字段。二者分开，使内核在覆盖结果之后，仍能为跟踪或系统调用重启等逻辑保留原始调用号。

内核现在有了可用的内核栈和寄存器现场，可以调用 C 代码，例如 do_syscall_64(regs, nr)。这一阶段的职责是准备执行环境，仍未完成具体的文件读取。

阶段三：内核分发并执行服务

进入 C 层后，内核先处理系统调用共有的逻辑，再执行 read 的具体实现。

入口处理与调用号分发

统一入口根据内核配置和线程状态，执行跟踪、过滤、审计等工作。例如，ptrace 用于调试与跟踪，seccomp 可以限制线程允许执行的系统调用。请求因此可能在实际执行前被修改或拒绝。

进入分发逻辑后，内核检查调用号是否有效。在 Linux 6.12 的原生 x86-64 路径中，有效编号交给 x64_sys_call(regs, nr) 分发；未被特殊入口逻辑处理的无效请求会得到 -ENOSYS，表示没有对应实现。[3]

内核维护调用号到实现入口的映射，但实际代码不一定是教材中常见的 sys_call_table[nr]()。不同版本可以使用函数指针表或生成的分发代码，稳定的是“按 ABI 和调用号定位服务”这一规则。

文件查找与读取

ksys_read() 根据 fd 获取内核中的 struct file 对象，并处理文件位置及相关同步，再调用 vfs_read()。VFS 是虚拟文件系统层，为不同文件类型提供统一操作接口。

vfs_read() 检查对象是否可读、用户地址范围和读取范围是否符合要求，以及是否通过相关安全检查。随后，它调用文件对象提供的 read 或 read_iter 方法。普通文件、管道和 socket 的具体实现不同，因此同一个系统调用可以读取不同类型的对象。[4]

对于普通文件的缓冲读取，数据可以直接来自页缓存，不一定需要实际访问存储设备；缓存缺失时，读取路径才需要进一步获取数据。

写入用户缓冲区

内核必须把用户传入的 buf 视为不可信地址。它可能未映射、不可写，或者在检查后被同一进程的其他线程取消映射。

数据写入用户空间时，需要使用受控的用户内存访问机制，例如 copy_to_user()，或者通过 iov_iter 等抽象完成。对于 read，方向是向用户缓冲区写入数据；copy_from_user() 则用于反方向读取用户提供的输入。

访问用户地址时也可能发生缺页。可修复的缺页由内存管理逻辑处理后重试；无法修复的访问错误通过异常修复路径报告给调用方。地址范围检查通过，不代表后续每一次内存访问都能成功。[5]

等待与结果

如果读取的数据尚未就绪，当前线程可以等待。例如，读取一个仍有写端、但暂时没有数据的阻塞管道时，线程通过等待队列和调度机制睡眠，让其他线程使用 CPU。数据到达后，它被唤醒，等再次获得 CPU 才继续原来的内核执行路径。

如果数据已就绪，读取可以直接完成，无需因等待数据而切换线程。

对于 read，完成后得到以下结果之一：

  • 正数：实际读取的字节数，可以小于请求长度；
  • 0：在非零长度请求等通常条件下，表示到达文件末尾或流结束；
  • 负错误码：读取失败，例如无效文件描述符对应 -EBADF。

分发层将结果写入 pt_regs 的 ax 字段。此时读取操作已完成，接下来处理如何恢复用户态执行。

阶段四：返回用户态并交付结果

系统调用处理函数返回后，CPU 仍在内核态。内核需要完成出口工作，恢复返回现场，再将结果交给 libc。

出口处理与现场恢复

出口路径处理跟踪、审计、待处理信号以及重新调度等事项，然后判断能否使用快速返回路径。

在这里讨论的 x86-64 路径中，满足返回地址、段状态和标志位等约束时，可以使用 sysretq；否则走更通用的 iretq 路径。这种选择涉及能否正确、安全地恢复现场，而不只是速度。[3]

内核出口汇编恢复 ABI 要求保留寄存器，准备用户栈和 GS 基址，并在需要时恢复用户侧页表。两种返回方式使用的现场来源不同：

  • sysretq 根据准备好的 rcx 和 r11 恢复指令地址和标志；
  • iretq 根据栈上的返回帧恢复指令地址、标志、栈等状态。

正常返回时，CPU 回到用户态，继续执行 libc 中 syscall 后面的指令，rax 保存原始结果。这里并不是所有的寄存器都原样恢复：rax 已变为结果，rcx、r11 在该 ABI 中属于被系统调用影响的寄存器。

libc 转换返回值

对于 read，libc 将非负结果直接返回给应用；如果收到负错误码，则设置线程局部的 errno，并返回 -1。errno 是应用读取具体错误原因的位置，例如 EBADF 表示文件描述符无效。[1]

细节与注意事项

权限切换不等于线程切换

系统调用通常在当前线程的进程上下文中执行，进入内核不会自动创建或切换到一个“内核服务线程”。阻塞、抢占或主动让出 CPU 等情况才会触发调度。系统调用也不等于硬中断处理，因此其中符合条件的代码可以睡眠。

用户内存访问有独立的失败语义

copy_to_user()、copy_from_user() 返回的是未复制的字节数，0 才表示全部完成。它们可能因缺页而睡眠，不能当作普通内存复制，在持有自旋锁等不可睡眠环境中随意调用。[5]

对复杂输入，常见做法是先复制到内核缓冲区，再校验并使用该副本，避免校验后重新读取已被用户修改的数据。不过，复制过程本身不保证多个字段构成原子快照，副本仍需完整校验。

系统调用不一定按原调用点直接返回

信号可能让线程先执行用户态信号处理函数。被打断的调用，根据接口语义、信号设置和是否已经完成部分工作，可以返回部分结果、向 libc 返回 -EINTR，或由内核安排重启。应用经 libc 看到的中断错误通常是返回 -1、errno 为 EINTR。

空管道也不总是阻塞：没有写端时，读取返回流结束；非阻塞管道在仍有写端但无数据时，通常返回 EAGAIN。exit 不返回，成功的 execve 转入新程序，因此四阶段中的“回到原调用点”只适用于正常返回的路径。

库函数、通用封装与指令不同

read() 是专用 libc 接口，syscall(SYS_read, ...) 是 libc 的通用封装，而汇编 syscall 是 CPU 指令。前两者通常都处理 errno；直接执行指令则必须自己处理原始返回值。

不能把 read 的“非负成功、负数失败”扩展为所有接口的规则。Linux x86-64 原始 ABI 使用保留的负错误码范围表示失败，具体接口仍需遵循自身返回约定。成功调用后也不能仅凭 errno 的旧值判断失败。

性能成本不只来自切换指令

系统调用的额外成本包括现场保存和恢复、入口与出口处理，以及条件性的页表切换。具体服务还会增加对象查找、数据复制、缺页、锁竞争和调度成本。这个过程不一定清空全部缓存，也不一定刷新全部 TLB 或切换线程。

架构与版本限定

文中提到的 rax、rcx、r11、swapgs 和 sysretq 属于 x86-64 下的指令，不能直接套到 ARM64 或 RISC-V 架构。其中“陷入”泛指主动受控进入内核，不意味着所有架构都使用软件中断指令。
