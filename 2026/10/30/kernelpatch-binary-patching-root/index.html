KernelPatch的实现原理

XR

发布于：2026年10月30日
次浏览

KernelPatch：在编译后的 Android 内核二进制上实现 Root

它解决什么问题

Android 上任何 Root 方案要回答的都是同一个问题：普通进程的提权请求由谁批准、在哪里批准。Linux 把进程的身份信息维护在内核里，包括 UID、GID、capabilities 以及安全模块状态。用户态进程不能自行修改这些信息；调用 setuid(0) 时，内核会先检查当前凭据是否允许变更。因此，所谓“提供 su”，本质是在内核执行路径中加入一套受控的授权与凭据变更逻辑。

实现这套逻辑有几种现成路线。Magisk 通过接管 ramdisk 中的 init、补充 SELinux 策略并运行特权守护进程，在用户空间提供 su，不修改内核。KernelSU 把授权逻辑放进内核，可以在内核源码中直接加入调用点后重新编译，也可以在 GKI 设备上以 LKM 形式加载。两者都有明确前提：前者能力主要停留在用户空间和挂载层；后者依赖源码集成条件，或受内核模块接口（KMI）和厂商模块加载策略约束。

KernelPatch 针对的是另一种情况：只有设备厂商编译好的、已被 strip 的内核镜像，没有可用源码，也不希望整体替换内核，却仍需要在内核中加入授权、提权和 Hook 能力。它直接修改内核二进制，完成符号定位、代码注入、控制流修改和运行时模块加载。KernelPatch 本身更接近底层补丁框架；在 Android 上，APatch 基于它提供镜像修补、授权管理和用户侧模块生态。

KernelPatch 当前官方说明主要面向 arm64，并要求内核启用 CONFIG_KALLSYMS。它没有绕过 Linux 的权限模型：真正改变进程身份时，仍然要使用内核自身的凭据机制。它改变的是“哪些代码能够在内核中执行，以及这些代码在什么时机介入”。

第二，KernelSU 普通模块和 KernelSU 内核核心不是同一层。KernelSU 的授权逻辑在内核中，但普通模块提供的系统文件、启动脚本和属性修改由 ksud 等用户空间组件通过 overlayfs、bind mount 等挂载机制呈现。KPM 则不同，它是直接运行在内核空间的补丁模块。

前置条件：为什么能从 stripped kernel 找到关键函数

正式发布的 Android 内核通常不携带完整调试符号和源码信息，但很多内核仍启用了：

kallsyms 在内核镜像中保留“符号名称到地址”的信息，用于内核自身的符号解析、调试和部分运行时机制。KernelPatch 可以据此定位一批关键符号，并结合字符串引用、函数指令特征、数据结构布局和架构调用约定，推断出补丁需要使用的对象，例如：

  • 凭据相关函数；
  • 系统调用表或系统调用路径；
  • 进程结构与当前任务访问方式；
  • 文件、内存、安全模块等子系统的关键函数；
  • 内核初始化路径和内存分配相关函数。

然而 kallsyms 可能不完整，结构体字段偏移、编译器优化和厂商修改仍需要适配。KernelPatch 官方也把“只使用 stripped Linux kernel image 获取符号信息并进行修补、Hook”作为项目的核心能力之一。

另一个前提是启动链允许被修改的镜像启动。Android Verified Boot（AVB）会沿硬件信任根、bootloader、启动镜像和受保护系统分区建立验证链。被修补的内核与原厂镜像哈希不同，在锁定 bootloader、严格执行原厂验证策略的设备上通常无法启动。解锁 bootloader 后，设备按其解锁策略接受修改镜像，但这不意味着所有运行时的安全机制都消失。

修补流程

解包启动镜像并取出内核

Android 的 boot.img 是一个启动镜像容器，包含镜像头、kernel、启动参数以及与设备版本相关的其他内容。Android 13 采用新布局的设备还可能把 generic ramdisk 拆分到独立的 init_boot.img。KernelPatch 修补的重点是其中的 kernel，而不是 Magisk 主要修改的 ramdisk/init。

定位补丁点并注入代码

仅有一段新增机器码追加在镜像末尾没有作用，CPU 不会自动执行它。补丁必须同时完成两件事：

  1. 将补丁运行时所需的代码和数据放入内核镜像可加载、可执行的位置；
  2. 修改原有控制流，使内核启动或相关系统调用路径能够进入补丁代码。

静态修补时，KernelPatch 会在生成新的启动镜像前完成这些修改。运行时扩展则由已经启动的补丁核心加载 KPM。官方项目将注入方式概括为静态修补内核镜像和运行时动态加载两类。

补丁代码需要处理自身的加载地址、符号引用、重定位、内存权限和必要数据区。它有别于标准 Linux .ko 模块，不能简单依赖普通模块加载器完成所有工作；KPM 的加载、内存分配和符号解析由 KernelPatch 自己的运行时支持。

实现时必须处理以下问题：

  • 被覆盖的指令必须按完整指令边界搬迁，不能截断；
  • PC 相对寻址、条件跳转、字面量池等指令搬到新位置后可能需要重写；
  • 单条直接跳转指令的范围有限，通常需要寄存器或跳板中转；
  • 要维护代码段的可执行权限并刷新指令缓存；
  • Hook 函数必须遵守调用约定、栈对齐和寄存器保存规则；
  • 内核可能在多核上并发执行，补丁安装阶段要避免其他 CPU 执行到半成品指令。

KernelPatch 还提供 syscall table hook。系统调用表是调用号到内核处理入口的映射，修改表项可以把指定系统调用导向补丁处理函数。不过，现代内核在配置、只读映射和导出策略上对系统调用表有更多限制，具体可行性依赖内核配置和架构实现。

Hook 解决了执行时机的问题。而补丁处理函数被调用后，还必须验证调用者的身份，再决定是否调整凭据、加载模块或改变某个内核操作的结果。没有这些控制，任意进程都能触发提权路径。

SuperCall：用户态与补丁内核的受控入口

KernelPatch/APatch 使用 SuperCall 表示用户态与补丁内核之间的特权请求通道，并使用 SuperKey 作为访问凭据。它的职责类似一个只对授权管理器开放的内核控制接口：

SuperCall 有包括类似系统调用在内的多种实现方式。而内核控制接口也可以有多种分发形式，实际项目版本可能通过特定调用入口、已有通用接口上的协议或内部 Hook 实现。对使用者而言，只需要提供一个稳定的接口：请求最终需要进入被修补过的内核，通过密钥和授权检查后，执行特权命令。

SELinux：改策略与 Hook 检查路径

Magisk 的方式更接近正面修改规则：在启动早期 patch sepolicy，加入自身需要的域和转换规则，使守护进程和 root shell 的访问在 SELinux 策略上成立。其结果比较容易从策略和进程上下文中解释。

区别于直接关闭 SELinux，关闭或放宽全局策略会扩大所有进程的攻击面；更精细的做法是只在特定调用者、特定操作和特定条件下改变判断结果。APatch 上层也可以结合 magiskpolicy 等工具补充用户空间兼容所需的策略规则。因此，内核 Hook 与策略 patch 在实际系统中未必互斥。

/system/bin/su 可以只是兼容入口

传统用户和脚本通过执行 su 请求 Root，但系统分区中不一定要永久存在这个文件。KernelSU 的历史实现就展示过一种兼容方式：在内核中拦截 execve、faccessat、stat 等路径，对已授权 UID 查询或执行 /system/bin/su 的请求进行重定向，再由内核侧改变凭据并转入自己的用户空间管理程序。

KernelPatch/APatch 可以通过自己的 SuperCall 和管理器协议提供 Root，同时根据兼容目标决定是否支持传统 su 命令。这里的关键区别是：

  • su 文件/命令是用户态看到的接口或触发方式；
  • 授权策略和凭据变更在内核补丁逻辑中完成；
  • root shell是凭据变更后继续运行的用户态程序。

KPM：在内核空间扩展行为

KPM（KernelPatch Module）是 KernelPatch 的内核模块，名称上类似 LKM，但不是内核原生的 .ko 加载体系。它由 KernelPatch 的加载器解析、重定位并在内核中执行。

KPM 与普通 Root 模块的边界

类型 运行位置 能力
Magisk 模块 用户空间 / 挂载层 覆盖系统文件、运行脚本、修改属性、配合 Zygisk
KernelSU 模块 / APM 用户空间 / 挂载层 overlayfs 或 bind mount、启动脚本、sepolicy 规则
KPM 内核空间 inline hook、syscall hook、访问内核数据结构

普通模块即使由 Root 工具安装，其脚本仍是用户态进程；KPM 的初始化和处理函数运行在内核态。一个系统文件替换需求不需要 KPM；只有需要改变内核函数行为或系统调用语义时，才需要 KPM。

加载方式

在 APatch 的使用模型中，KPM 大体有三类形式：

  1. 嵌入内核：补丁镜像生成时就把 KPM 合入，随内核启动加载，重启后仍在；
  2. 运行时加载：系统启动后立即装入内核，马上生效，重启后默认消失；
  3. 安装到数据分区：由上层管理器在指定启动阶段或事件中加载。

运行时加载器需要完成：

  • 读取模块镜像并校验格式；
  • 分配具有合适权限的内核内存；
  • 处理符号引用和重定位；
  • 建立模块元数据和卸载信息；
  • 调用模块初始化函数；
  • 在卸载时恢复 Hook、释放资源并处理引用。

一个 KPM 可以注册自己的 inline hook。例如在 execve 路径上记录执行事件，或在文件访问路径上按规则改变行为。由于它直接运行在内核态，因此模块缺陷造成的后果可能不止是普通 App 崩溃，也可能是立即 kernel panic 或内存破坏。

与 KernelSU 源码集成的对照

KernelSU 和 KernelPatch 最终都可以在内核态修改凭据，但加入内核的方式不同。

源码或 LKM 路径

KernelSU 集成到可构建的内核源码中时，可以：

  • 加入 KernelSU 内核源码并启用配置；
  • 直接在 execve、文件访问等路径插入处理调用；
  • 或通过 kprobe 在指定内核函数上注册处理函数；
  • 由管理器维护应用授权，内核按授权结果改变凭据和环境。

在 LKM 模式下，KernelSU 编译成符合目标内核 KMI 的模块，由启动阶段加载进原厂内核。其优点是不整体替换内核，但模块必须与内核 ABI/KMI、符号和配置兼容。

安全边界与实际风险

内核态模块没有普通应用意义上的沙箱

KPM 运行在内核态，可以访问内核内存、修改函数执行路径并影响系统全部进程。模块中的空指针、并发错误或错误的 Hook 恢复逻辑都可能导致不可恢复的内核崩溃。来源不可信的 KPM 与恶意内核代码没有本质区别。

隐蔽性不等同于不可检测

内核二进制补丁不会像传统 system root 那样直接在 /system 中留下 su 文件，但仍可能留下可观测痕迹：

  • 启动镜像或内核代码段的完整性变化；
  • 函数入口指令与原始内核不一致；
  • 新增可执行内存或异常内存权限；
  • syscall table、函数指针或关键数据结构变化；
  • KPM 持久化文件和管理器数据；
  • 启动阶段、SELinux 行为或系统调用时序差异。

AVB、dm-verity、启动链度量、内核完整性检测、强反作弊和厂商安全环境都可能从这些维度发现修改。所谓内核方案更隐蔽，只是检测位置从用户空间文件和挂载痕迹转移到了启动镜像与内核运行时状态。

兼容性问题发生在更底层

常见失败点包括：

  • 内核未启用 CONFIG_KALLSYMS，符号信息不足；
  • 压缩格式、镜像头或厂商封装不被修补工具识别；
  • 编译器优化导致预期函数模式变化；
  • 结构体布局或函数签名与适配版本不一致；
  • inline hook 重定位处理不完整；
  • SELinux、厂商安全加固或内核保护机制阻止相关操作；
  • 刷入与设备 KMI、安全补丁级别或 A/B 槽位不匹配的镜像。

内核补丁一旦不兼容，故障通常比用户空间模块更严重：卡首屏、无限重启、kernel panic，甚至需要重新刷入原厂镜像恢复。

权限模型仍需最小化

即使技术上可以 Hook 大量内核函数，也不应让所有请求无条件通过。合理设计至少包括：

  • SuperKey 不暴露给未授权应用；
  • 提权命令需要调用者身份校验和用户确认；
  • KPM 加载仅限管理器控制的可信路径；
  • Hook 处理函数默认走原逻辑，只对明确条件生效；
  • 模块卸载时必须恢复原始函数入口和引用状态；
  • 保留原厂启动镜像和可用恢复方案。

适用场景与选择

KernelPatch/APatch 适合的场景是：

  • 无法获得可构建的设备内核源码；
  • 不希望整体替换成另一个 GKI kernel；
  • 需要保留厂商内核主体及其内置驱动和配置；
  • 需要 inline hook、syscall hook 或 KPM 这类内核态扩展；
  • 用于 Android/Linux 内核安全研究、系统行为分析或受控设备定制。

如果需求只是运行常规模块、修改系统文件、使用 LSPosed/Zygisk 生态或管理应用 Root 授权，Magisk 或 KernelSU 通常更成熟，故障面也更容易隔离。只有当问题明确发生在内核函数或系统调用层，才应该考虑 KernelPatch 的二进制补丁能力。

小结

KernelPatch 的核心可以概括为四点：

  1. Root 的关键在内核授权：用户态 su 只是入口，真正的 UID、capabilities 和安全状态由内核维护和变更。
  2. 它修改的是编译后的内核：从 boot.img 中取出 stripped kernel，借助 kallsyms 和二进制分析定位关键函数，再注入代码并修改控制流。
  3. Hook 与 SuperCall 是基础：Hook 让补丁逻辑在正确的内核时机运行，SuperCall 让管理器通过受控通道请求提权和加载 KPM。
  4. 能力与风险同在最底层：KPM 可以直接改变内核行为，但错误代价是可能的 kernel panic，且启动校验和完整性检测不会因为补丁运行在内核态而消失。

与 Magisk 不同，KernelPatch 是把 Root 和系统扩展的实现位置从用户空间、源码集成进一步推进到了厂商内核二进制本身。所以简单来说，现有的三种主流的 root 方案（Magisk、KernelSU 和 KernelPatch）之间的差别主要是在 Android/Linux 权限栈的哪一层建立信任和授权机制。
